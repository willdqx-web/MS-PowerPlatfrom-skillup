## 0. 今日のゴール

昨日は「自分の PC の中のファイル整理」を自動化しました。

## 1. 機能・概念の解説

### 1-1. ブラウザ自動化のしくみ

PAD はブラウザに**拡張機能**を通じて命令を送ります。「この入力欄に文字を入れる」
「このボタンを押す」といった指示を、画面上の部品を指定して行います。

初回のみ、ブラウザ拡張機能の有効化が必要です（ステップ演習1 で行います）。

### 1-2. UI 要素とは

PAD が「画面のどの部分か」を見分けるための情報を **UI 要素**と呼びます。
「画面の左から 300 ピクセル、上から 200 ピクセルの場所」ではなく、
**「id が `applicant` の入力欄」**のように、部品そのものを指し示して覚えます。

> **なぜ座標で覚えないのか**: 座標で覚えると、ウィンドウサイズが変わっただけで壊れます。
> 部品そのものを指定すれば、多少レイアウトが変わっても動き続けます。
> ただし、**Web ページ側が改修されると壊れる**という弱点は残ります（1-6 で重要になります）。

### 1-3. 今日使う主なアクション

左のアクションペインの「ブラウザー自動化」の中にあります。

| アクション | 何をするか |
|------------|-----------|
| 新しい Microsoft Edge を起動する | ブラウザを開く |
| Web ページ内のテキスト フィールドに入力する | 入力欄に文字を入れる |
| Web ページのボタンを押します | ボタンをクリックする |
| Web ページからデータを抽出する | **表や一覧を丸ごと取り出す**（今日の主役） |
| Web ページ上の要素の詳細を取得します | 特定の 1 か所の文字を取り出す |
| Web ページのコンテンツを待機します | **表示されるまで待つ**（1-4 参照） |
| Web ブラウザーを閉じる | ブラウザを閉じる |

### 1-4. 待機処理：自動化がいちばん失敗する理由

自動化が失敗する原因で最も多いのが、**「まだ表示されていないものを操作しようとする」**ことです。

人間は画面を見て「まだ出ていないな」と分かりますが、PAD は待ってくれません。
ページを開いた**次の瞬間**に表を読もうとして、「そんな要素は無い」とエラーになります。

対策は 2 つあります。

| 方法 | 内容 | 評価 |
|------|------|------|
| 固定時間待つ | 「5 秒待機」を入れる | 簡単だが、遅いときは失敗し、速いときは無駄に待つ |
| **条件がそろうまで待つ** | 「この要素が表示されるまで待つ」 | **こちらが正解**。速いときは即進み、遅いときは待つ |

今日の練習ページは、**わざと 1.5 秒遅れて**一覧が表示されるように作ってあります。
待機処理の必要性を体で理解するためです。

### 1-5. エラー処理の初歩

昨日までは「うまくいく前提」でフローを作ってきました。実務ではそれでは通用しません。

PAD では、各アクションの左下にある「**エラー発生時**」から動作を指定できます。

| 設定 | 意味 | 使いどころ |
|------|------|-----------|
| フローの実行を停止する（既定） | エラーで止まる | 途中で止まると困る処理 |
| **フローの実行を続行する** | 無視して次へ進む | 失敗しても構わない処理 |
| **再試行** | 何回か試し直す | 通信・画面表示など、時々失敗するもの |

> **なぜエラー処理を最初から学ぶのか**: 「動くものを作る」のは半分で、
> 「**壊れたときに困らないようにする**」のがもう半分です。これは Day8 以降のクラウド編でも
> 合格ラインとして必ず求められます。今日はその入口です。

### 1-6. 今日の最重要：PAD とクラウド、どちらを使うべきか

明日（Day3）からはクラウド（Power Automate / SharePoint）に進みます。
その前に、**使い分けの判断基準**をはっきりさせておきます。

**原則: 正規の入口（コネクタ・API）があるなら、必ずそちらを使う。無いときだけ PAD。**

| | PAD（画面を操作する） | クラウド（コネクタで繋ぐ） |
|---|---|---|
| つなぎ方 | 人間と同じように画面を操作 | システム同士が正規の窓口で直接やり取り |
| 壊れやすさ | **画面が変わると壊れる** | 画面が変わっても影響しない |
| 動作条件 | **PC が起動しログインしている必要** | クラウド上で自動実行（PC 不要） |
| 速度 | 遅い（画面の描画を待つ） | 速い |
| 向く相手 | 古い社内システム、API の無い Web | SharePoint / Excel / Outlook / Forms / Teams |

#### 判断のフローチャート

1. その相手に**コネクタはあるか？** → あるなら**クラウド**（迷う必要なし）
2. コネクタは無いが、**CSV/Excel の出力機能はあるか？** → あるならファイル経由でクラウド
3. どちらも無い → **PAD**

> ⚠️ **今日いちばん避けてほしい失敗**: PAD を覚えた直後は、何でも画面操作で自動化したく
> なります。しかし SharePoint や Excel をわざわざ画面操作で自動化するのは、
> **正面玄関があるのに窓から入るようなもの**です。脆く、遅く、PC を占有します。
> 「PAD は最後の手段」と覚えてください。

## 2. ステップ演習1: ブラウザ自動化の準備（目安30分）

### 2-1. 練習ページを開いて中身を確認する

1. このフォルダの `day2_社内ポータル.html` を**ダブルクリック**して開く
2. 「読み込み中です...」と表示された **約 1.5 秒後**に、申請一覧の表が現れることを確認する
3. 表の行数を数える（この後の答え合わせで使います）
4. ブラウザのアドレスバーに表示されている **URL（`file:///...`）をコピーしてメモしておく**
   → PAD でこの URL を指定します

#### 確認用の答え合わせ（一覧の中身）
| 項目 | 値 |
|------|-----|
| 全行数 | 12 |
| ステータスが「承認済」 | 5 |
| ステータスが「申請中」 | 4 |
| ステータスが「承認待ち」 | 2 |
| ステータスが「却下」 | 1 |
| 影響度が「高」 | 3 |

### 2-2. ブラウザ拡張機能を有効にする

1. PAD を起動し、新しいフロー `Day2_Web練習` を作成する
2. アクションペインの「ブラウザー自動化」→「**新しい Microsoft Edge を起動する**」をドラッグ
3. この時点で拡張機能の案内が出たら、指示に従って有効化する
   （PAD メニューの「ツール」→「ブラウザー拡張機能」からも設定できます）
4. 設定する
   - 起動モード: `新しいインスタンスを起動する`
   - 初期 URL: 2-1 でメモした `file:///...` の URL を貼り付ける
   - 生成された変数: `Browser`（既定のまま）
5. 保存して実行する → ブラウザが自動で開き、練習ページが表示されれば成功です

## 3. ステップ演習2: 一覧データを抽出して CSV に保存する（目安60分）

今日の主役です。画面の表を丸ごと取り出します。

### 3-1. まず「待たずに」やってみる（失敗を体験する）

1. 「ブラウザー自動化」→「データ抽出」→「**Web ページからデータを抽出する**」を、
   ブラウザ起動の**下**にドラッグする
2. アクションの設定画面が開いたら、**ブラウザ側の画面に切り替える**
3. 表の 1 行目にマウスを重ねると赤枠が出るので、**右クリック**する
4. メニューから「**要素の値を抽出**」→「**HTML テーブル全体**」を選ぶ
   → PAD 側のプレビューに 12 行分のデータが表示されます
5. 「終了」→「保存」で設定を確定する
   - 保存先: `データ テーブル`（変数 `DataFromWebPage`）
6. **ブラウザを閉じてから**、フローを実行する

> ここで **エラーになる、または 0 行しか取れないことがあります**。
> 原因は、ページを開いた直後にはまだ表が表示されていないからです（1-4 で説明した典型的な失敗）。
> これを次で直します。**失敗を見ておくことが目的**なので、成功してしまった場合も次に進んでください。

### 3-2. 待機処理を入れて安定させる

1. 「ブラウザー自動化」→「**Web ページのコンテンツを待機します**」を、
   ブラウザ起動とデータ抽出の**間**にドラッグする
2. 設定する
   - ページ上の要素: 一覧テーブルを指定する（3-1 と同じ要領で、表を右クリックして選択）
   - 動作: `要素が表示されるまで待機します`
   - タイムアウト: `30` 秒
3. 保存して実行する
   → 今度は毎回安定して 12 行が取れるようになります

4. 実行後、右の変数ペインで `DataFromWebPage` をダブルクリックし、
   **12 行のデータが入っていること**を確認する

### 3-3. CSV ファイルに保存する

1. 「ファイル」→「**CSV ファイルに書き込む**」をフローの最後にドラッグする
2. 設定する
   - 書き込む変数: `%DataFromWebPage%`
   - ファイル パス: `デスクトップ\PAD演習_Day2\申請一覧.csv`
     （フォルダが無い場合は、先に「フォルダーの作成」アクションを追加してください）
   - エンコード: `UTF-8`
   - 列見出しを含める: **オン**
3. 実行し、できあがった CSV を Excel で開いて確認する

#### 確認用の答え合わせ（出力された CSV）
- データ行数: **12 行**（見出し行を除く）
- 1 行目のデータ: `A001 / 2026-06-01 / 中村 彩 / P001 / 図面修正 / 中 / 承認済`
- 最終行のデータ: `A012 / 2026-06-18 / 中村 彩 / P003 / 図面修正 / 低 / 申請中`

> **ここで起きたこと**: これまで「画面を見ながら Excel に手で打ち直していた」作業が、
> ボタン 1 つになりました。これが Web 情報収集の自動化です。

## 4. ステップ演習3: フォームへの入力を自動化する（目安60分）

今度は逆に、画面へ**書き込む**自動化です。

### 4-1. 入力欄に値を入れる

新しいフロー `Day2_申請登録` を作成し、次の順に組みます。

1. 「新しい Microsoft Edge を起動する」（初期 URL は練習ページ）
2. 「**Web ページ内のテキスト フィールドに入力する**」
   - UI 要素: 「申請者氏名」の入力欄を指定（ブラウザ画面で右クリック →「要素の追加」）
   - テキスト: 自分の名前
3. 「**Web ページでドロップダウン リストの値を設定します**」を 3 つ追加する

| 対象のドロップダウン | 設定する値 |
|----------------------|-----------|
| 案件コード | `P004 配管ルート再設計` |
| 変更種別 | `図面修正` |
| 影響度 | `中` |

4. 「Web ページ内のテキスト フィールドに入力する」をもう 1 つ追加
   - UI 要素: 「変更概要」のテキストエリア
   - テキスト: `配管ルートの干渉箇所を修正`

### 4-2. ボタンを押して結果を受け取る

1. 「**Web ページのボタンを押します**」を追加し、「申請を登録する」ボタンを指定する
2. 「**Web ページ上の要素の詳細を取得します**」を追加する
   - UI 要素: **受付番号の値そのもの**（登録後に太字で表示される `R-0001` の部分）を指定する
   - 属性: `Own Text`
   - 生成された変数: `AttributeValue`
3. 「メッセージを表示」を追加し、`%AttributeValue%` を表示する
4. 実行する

> **ポイント: 取り出したい値そのものの要素を指定する**
> 「登録が完了しました。受付番号: R-0001」という**行全体**を指定したくなりますが、それは避けます。
> `Own Text` は「その要素が直接持っている文字」だけを取り出す属性で、**中に入っている別の部品の
> 文字は含まれません**。行全体を指定すると、肝心の受付番号が抜け落ちてしまいます。
> 欲しい値だけが入っている一番内側の要素を狙うのが、確実で壊れにくいやり方です。

#### 確認用の答え合わせ
- ページ上に「登録が完了しました。」「受付番号: **R-0001**」と表示される
- メッセージボックスには **`R-0001`** だけが表示される（余計な文字が付いていなければ、
  要素の指定が正しくできています）

> ※ 受付番号はページを開き直すたびに `R-0001` から始まります。
> 同じページで 2 回登録すると `R-0002` になります。

### 4-3. エラー処理を入れる

「ボタンを押す」アクションで、押す相手が見つからないと止まってしまいます。ここを守ります。

1. 「Web ページのボタンを押します」をダブルクリックし、左下の「**エラー発生時**」を開く
2. 「**再試行**」を選び、`2` 回・`3` 秒間隔に設定する
3. 保存して、もう一度実行する（正常時の動作が変わらないことを確認）

> 実務では「時々失敗するが、やり直せば通る」処理が非常に多くあります。
> 再試行を入れておくだけで、自動化の安定性は大きく変わります。

## 5. 応用課題（自力で取り組んでください）

ここからは手順の細かい指示はありません。1〜4 章を活かして、自分で考えて取り組んでください。

1. **必須入力チェックの挙動を確認する**
   申請者氏名を**空のまま**登録ボタンを押すフローを作り、表示されたエラーメッセージを取得して
   メッセージボックスに表示する。
   （ヒント: 今度は受付番号ではなく、メッセージが表示される要素を指定します）

2. **抽出したデータを絞り込んで保存する**
   一覧 12 件のうち、**ステータスが「申請中」の行だけ**を別の CSV
   （`申請中一覧.csv`）に書き出す。
   （ヒント: 抽出したデータテーブルを `For each` で回し、`If` で判定してから
   新しいリストに追加します）

3. **1 つのフローにまとめる**
   「一覧を抽出して CSV 保存 → 新規申請を 1 件登録 → ブラウザを閉じる」を
   1 本のフローとして完成させる。最後に「処理が完了しました」と表示する。

4. **（重要・自力で考える）使い分けの判断を書く**
   今日自動化した「社内ポータルからの一覧取得」について、次の 2 つの場合それぞれで
   PAD とクラウドのどちらを選ぶべきか、**理由つきで**メモに書く。
   - ケース A: そのシステムに SharePoint コネクタが用意されている場合
   - ケース B: 古い社内システムで、CSV 出力機能も API も無い場合

#### 応用課題の答え合わせ
- 課題 1: `入力エラー: 申請者氏名・案件コード・変更種別・影響度は必須です。` が表示される
- 課題 2: `申請中一覧.csv` のデータ行数は **4 行**（A003 / A007 / A009 / A012）
- 課題 4: 模範解答は次のとおり
  - **ケース A → クラウド**。正規の窓口があるため、画面改修の影響を受けず、PC を起動して
    おかなくても自動実行できる。画面操作でやる理由がない。
  - **ケース B → PAD**。正規の入口が無いため、人間と同じ画面操作で取りに行くしかない。
    ただし画面改修で壊れる前提で、エラー処理と定期的な動作確認をセットにする。
