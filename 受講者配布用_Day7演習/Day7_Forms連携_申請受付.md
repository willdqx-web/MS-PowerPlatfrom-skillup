## 0. 今日のゴール

Day4 では、申請を「手動トリガー」で 1 件ずつ登録しました。でも実際の現場では、**申請する人自身が
入力してくれる入口**があると便利です。今日はその入口を **Microsoft Forms** で作ります。

今日の業務シナリオは「**設計変更申請フォームに回答されたら、自動で台帳（Excel）に記録し、
申請者に受付メールを返す**」です。

- Microsoft Forms で申請フォームを作れる
- **自動トリガー「新しい応答が送信されたとき」**を使える
- **「応答の詳細を取得する」**で回答内容を取り出せる
- 回答を `T_設計変更申請` に自動記録できる
- 受付確認メールを自動送信できる

まず1章を読んでから、2章以降のステップ演習に進んでください。

## 1. 概念の解説

### 1-1. Forms は「申請の入口」

Microsoft Forms は、アンケートや申請フォームを簡単に作れるツールです。今回は「設計変更申請」の
入口として使います。回答されると、その内容を Power Automate が受け取って処理できます。

### 1-2. 自動トリガー（何かが起きたら動く）

Day4 は「手動トリガー」（自分がボタンを押す）でした。今日は **自動トリガー**を使います。
「**フォームに新しい応答が送信されたとき**」に、フローが自動で動き出します。

| トリガー | いつ動くか |
|----------|-----------|
| 手動（Day4） | 自分がボタンを押したとき |
| **自動（今日）** | **フォームに回答が来たとき**（自動で反応） |

### 1-3. 「応答の詳細を取得する」

トリガーだけでは「回答が来た」ことしか分かりません。**回答の中身**（誰が・どの案件・影響度…）を
取り出すには、「**応答の詳細を取得する**」アクションを続けて使います。取り出した各項目は、
動的コンテンツとして後のアクションで使えます。

### 1-4. 申請IDは自動で採番する

フォームで申請者に申請IDを入力させると、重複や書き間違いが起きます。そこで**申請IDはフローが
自動で作ります**（式で、日時から一意な文字列を生成）。人に任せない、という設計の工夫です。

## 2. ステップ演習1: 申請フォームを作る（目安40分）

1. `https://forms.office.com` を開きサインインする
2. 「新しいフォーム」を作成し、タイトルを `設計変更申請` にする
3. 次の 6 問を追加する（**種類と選択肢は下表の通りに**）

   | # | 質問 | 種類 | 選択肢／備考 |
   |---|------|------|--------------|
   | 1 | 申請者社員ID | テキスト | 例: E103 |
   | 2 | 案件コード | 選択肢 | P001 / P002 / P003 / P004 / P005 / P006 |
   | 3 | 変更種別 | 選択肢 | 仕様変更 / 部品変更 / 図面修正 / コスト変更 |
   | 4 | 影響度 | 選択肢 | 高 / 中 / 低 |
   | 5 | 変更概要 | テキスト（長文）| |
   | 6 | 希望完了日 | 日付 | |

4. 右上「プレビュー」で見た目を確認する

> **なぜ選択肢にするのか**: Day3 の入力規則と同じ理由です。自由入力だと表記ゆれが起きるので、
> 案件コード・変更種別・影響度は選択肢にして、決まった値だけが来るようにします。

## 3. ステップ演習2: 回答を自動で台帳に記録する（目安60分）

### 3-1. 自動フローを作る

1. `https://make.powerautomate.com` →「＋作成」→「**自動化されたクラウド フロー**」
2. フロー名を `Day7_申請受付` とし、トリガーは「**新しい応答が送信されたとき**」
   （Microsoft Forms）を選ぶ
3. トリガーの「フォーム ID」で、作成した `設計変更申請` を選ぶ

### 3-2. 回答の詳細を取得する

1. 「＋新しいステップ」→「Microsoft Forms」→「**応答の詳細を取得する**」
   - フォーム ID: `設計変更申請`
   - 応答 ID: 動的コンテンツ「**応答 ID**」（トリガーの出力）

### 3-3. 申請IDを式で作る

1. 「作成」を追加し、式で申請IDを作る
   ```
   concat('F', formatDateTime(convertFromUtc(utcNow(),'Tokyo Standard Time'),'MMddHHmmss'))
   ```
   → `F0724103015` のような、フォーム由来と分かる一意な ID になります
2. この「作成」の名前を `申請ID` にする

### 3-4. T_設計変更申請 に記録する

1. 「Excel Online (Business)」→「**表に行を追加**」
   - ファイル: `設計変更管理.xlsx` / テーブル: `T_設計変更申請`
   - 各列に割り当てる:

     | 列 | 値 |
     |----|-----|
     | 申請ID | 動的コンテンツ「出力」（作成＝申請ID） |
     | 申請日 | 式 `convertFromUtc(utcNow(),'Tokyo Standard Time','yyyy-MM-dd')` |
     | 申請者社員ID | 応答の詳細「申請者社員ID」 |
     | 案件コード | 応答の詳細「案件コード」 |
     | 変更種別 | 応答の詳細「変更種別」 |
     | 変更概要 | 応答の詳細「変更概要」 |
     | 影響度 | 応答の詳細「影響度」 |
     | 希望完了日 | 応答の詳細「希望完了日」 |
     | ステータス | 固定文字 `申請中` |

### 3-5. 受付確認メールを送る

1. 「メールの送信 (V2)」を追加
   - 宛先: 自分のメール（本来は申請者。今回はテストなので自分宛）
   - 件名: `設計変更申請を受け付けました`
   - 本文: 申請ID・案件コード・影響度・申請日を差し込む

## 4. ステップ演習3: テスト（フォームから 2 件出す）（目安30分）

フローを保存したら、**フォームから実際に 2 件回答**して動作を確認します。

- 1 件目: 申請者社員ID `E103` / 案件コード `P001` / 変更種別 `図面修正` / 影響度 `中` /
  変更概要 `寸法の修正` / 希望完了日 任意
- 2 件目: 申請者社員ID `E106` / 案件コード `P006` / 変更種別 `仕様変更` / 影響度 `高` /
  変更概要 `材質の変更` / 希望完了日 任意

回答するたびに、フローが自動で動きます（数分かかることがあります）。

#### 確認用の答え合わせ
- `T_設計変更申請` に、**申請IDが `F` で始まる行が 2 行**増える
- 2 行とも ステータスは `申請中`、申請日は当日
- 1 行目は影響度 `中`・案件 `P001`、2 行目は影響度 `高`・案件 `P006`
- 受付確認メールが 2 通届く
- フローの実行履歴が成功（緑）になっている

## 5. 応用課題（自力で取り組んでください）

1. **影響度が高なら、通知も出す**
   Day4 で作った条件分岐を思い出し、影響度＝高の申請だけ `通知ログ` にも記録する。
2. **必須未回答への備え**
   フォームの必須設定（各質問を「必須」に）を見直し、空欄で登録されない工夫を確認する。
3. **（発展）受付番号を本文に**
   受付メールの本文に、自動採番した申請ID（`F…`）を「受付番号」として明記する。

#### 応用課題の答え合わせ
- 課題 1: 2 件目（P006・高）だけ `通知ログ` に記録される
